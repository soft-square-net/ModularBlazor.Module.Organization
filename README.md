# ModularBlazor.Module.Organization

Organization: a runtime module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform)
platform, in [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture) layers (generated from the
`platform-module-ca` template). It holds the newsroom's organization model: customer orgs, their unit tree
(Org > Sector > Department > Section), the people in it and their positions, and the tenant seeds that say which units
get a tenant of their own.

The module runs in one of two modes (setting `Organization:Mode`):

- **Central** (one deployment, the Organization service): owns the platform-level `organization` database and the
  management API below. It runs the connector too, for its own tenants.
- **Connector** (the default, every other deployment): pulls the central service's seeds and feeds into a replica in
  each tenant's database, serves the seeds to the host, writes the positions' grants, republishes the `org.*` events
  locally and serves the tenant's units (see "The connector").

**Operator docs**, in English and Arabic: [docs/en](docs/en/README.md) · [docs/ar](docs/ar/README.md) (setup of the
central and connector deployments, the settings reference, tenant seeds, tenant links, troubleshooting).

## The central database

The central service keeps one platform-level database, not one per tenant: server `Organization:DatabaseServer`
(default `TenantStore`, a server from the platform's `TenantDatabases`) and database `Organization:DatabaseName`
(default `organization`), schema `organization` (table prefix `organization_` on MySQL and Oracle). On start, a
background migrator creates the database if needed and applies the module's migrations (PostgreSQL, SQL Server,
MySQL, Oracle), retrying every 30 seconds while the server is unreachable. The endpoints are `TenantOptional`: no
tenant is needed to call them.

## Authorization

Endpoints only require a signed-in caller. What the caller may do is decided from the service's own data, never from
tenant permissions:

- **Platform admins** (role `platform-admin`) create orgs and may do everything.
- **Org admins** (the org's admin list, by issuer and subject) manage their whole org.
- **Positions**: a membership in a unit with a position gives the position's permissions on that unit and every unit
  below it. The seeded positions are `unit-admin` (`org.units.manage`, `org.members.manage`, `org.seeds.manage`) and
  `manager` (`org.units.manage`, `shifts.manage`). Any member may read their org (`org.read`).
- **Service clients** (`Organization:ServiceClients`, by `sub`, `client_id` or `azp`) read deployment seeds and the
  event feed, and report seed status.

Tokens are accepted only from `Organization:TrustedIssuers` (comma-separated; empty trusts the platform's issuer).

## The API (under `/api/organization`)

| Route | What |
| --- | --- |
| `GET/POST /orgs`, `GET/PUT /orgs/{orgId}`, `PUT /orgs/{orgId}/admins` | orgs you can see; create (platform admins: seeds the unit types, positions and root unit) |
| `GET/POST /orgs/{orgId}/unit-types` | the unit types and which types each may sit under |
| `GET/POST /orgs/{orgId}/units`, `GET/PUT/DELETE .../units/{unitId}`, `POST .../move`, `GET .../tenant` | the tree; a Section holds at least one Content category id, or `*` alone for all categories ([docs](docs/en/categories.md)); moving rebases the subtree; `tenant` is the unit's owning tenant seed |
| `GET/POST /orgs/{orgId}/persons`, `PUT .../persons/{personId}` | people (identity issuer and subject, optional employee profile) |
| `GET/POST /orgs/{orgId}/memberships`, `PUT/DELETE .../memberships/{membershipId}` | a person in a unit, with an optional position and dates; one primary per person |
| `GET/POST /orgs/{orgId}/positions`, `PUT .../positions/{positionId}` | position definitions and their permissions |
| `GET/POST /orgs/{orgId}/seeds`, `PUT .../seeds/{seedId}` | tenant seeds: a unit that gets its own tenant in a deployment; each edit is a new version |
| `GET /seeds?deployment=`, `POST /seeds/{seedId}/reports` | a deployment's seeds and its connector's status reports (per version, with history) |
| `GET /orgs/{orgId}/events?after=&take=` | the org's `org.*` v1 event feed, written in the same save as each change |
| `GET /orgs/{orgId}/links` | tenant links (skeleton) |

Every write takes the item's `version` and answers 409 if it changed since. Other modules use the
`Organization.Contracts` package: its `UnitScopes.For(path)` gives the `unit:{id}` scope of every unit on a path.

- **Times are UTC.** Every `DateTimeOffset` the module stores is normalized to UTC (offset zero, the same instant):
  the membership `from`/`until` a client sends in its local offset, and everything else through a model-wide
  converter on both DbContexts (PostgreSQL's `timestamptz` refuses other offsets). Answers carry UTC times.
- **Database failures.** A save that breaks a unique key (the same key twice, a second primary membership) or refers
  to a removed row is a 409 that says so. Anything else the database refuses is a 500 "Not saved" with the exception
  type only; the full error is in the server log.
- **Live.** After each committed change of an org (its units, unit types, persons, memberships, positions, seeds and
  links) the service publishes one `org.changed` message on the topic `organization:org:{orgId:N}`
  (`OrgLiveTopic` in Contracts), with the payload `{ type, id }` (the changed item, or `{ "type": "org", "id": orgId }`
  for several) and no sequence. It is sent in the tenant of the request that made the change (none outside a
  tenant); each deployment's connector sends it again in its tenants once it applies the change. The Units page
  reloads on it. Subscribers need `org.read` on `org:{orgId:N}` or on the org's root unit; no position gives it, so
  in a connector tenant it has to be granted by hand for now ([Troubleshooting](docs/en/troubleshooting.md)).

## The connector

Every deployment runs it; it is active once `Organization:CentralUrl` names the central service's module route
(`https://central.example/api/organization/`).

- **Service client.** It calls the central service with a client-credentials token: `Organization:TokenEndpoint`,
  `Organization:ClientId` (one of the central service's `Organization:ServiceClients`), `Organization:ClientScope`,
  and `Organization:ClientSecret`. Keep the secret out of the module catalog: set it in the host's configuration as
  `Modules:Settings:organization:Organization:ClientSecret`.
- **Seeds.** It is the platform's `ITenantSeedSource`: the host's reconciler pulls the deployment's seeds through it
  and reports their status back to the central service. Every `Organization:PollInterval` (30 s) it pulls the seeds
  itself, and when one is new or has a new version it publishes `tenancy.seed-changed.v1` through a tenant's outbox, so
  the host reconciles at once. The deployment id is `Organization:DeploymentId`, or the one the host's reconciler asks
  for (`Platform:DeploymentId`).
- **Replica.** For each active tenant created from one of those seeds, it applies the org's feed to the tenant's
  replica (schema `organization`, tables `replica_*`): every unit of the org (so moves need no call), the org's
  persons and positions, the memberships of the tenant's own units (its seed's root unit and below), and the links
  that name its seed. A new tenant gets its first sync before the module serves it. One replica at a time syncs a
  tenant (a lock in the tenant's database). When the central service is down, the replicas keep serving.
- **Feed cursor.** The feed's ids come from an identity column, so an entry can commit after a higher id was read.
  The connector reads again from a cursor that stays `Organization:FeedOverlap` (1 minute) behind, and applies each
  entry once (`FeedWindow`). A change that takes longer than the overlap to commit could be missed.
- **Grants.** Each membership of a tenant unit with a position gives that position's permissions as standing grants
  on `unit:{id}`, under the grant source `org:{unitId}`, replaced whenever the unit's memberships or the position change.
- **Events.** It republishes `org.unit-created/updated/moved/removed`, `org.membership-changed`,
  `org.person-changed`, `org.position-changed` and `org.tenant-link-changed` (v1, the central records as they are)
  through the replica's outbox, with the unit path, for the tenant's units and the root's ancestors.
- **Reads.** `IUnitDirectory` (in `Organization.Contracts`) over the replica: the module uses it directly, other
  modules through `HttpUnitDirectory` and the local API below. A unit's `CategoriesOf` is its own (a Section) or those
  of the tenant's units below it; `["*"]` when one of them serves all categories (`UnitCategories` in Contracts).
- **Live.** The manifest declares the platform's `unit` topic kind and the module's `org` kind, both with `org.read`.
  The module's `ILiveScopeResolver` works from the subscriber's tenant replica, never from the client, and fails
  closed (unknown keys get no scopes, so only the exact scope counts): a `unit:{id}` topic gets the scopes of the unit
  and its ancestors; `organization:org:{orgId:N}` gets the org's root unit `unit:{root}` when the tenant's replica
  follows that org (a grant below the root does not count: the topic speaks for the whole org). After each applied
  feed page it publishes to the changed units' topics and their ancestors', and one `org.changed` message on the org
  topic, all without a sequence (the feed's ids are not contiguous per topic). **Load the module on the core pool
  too**: the live hub runs there, and without the module on the hub's replica only the exact scope counts.

| Local route (tenant required, signed in) | What |
| --- | --- |
| `GET /local/units` | the tenant's units and its root unit's ancestors (`inTenant: false`), root first |
| `GET /local/units/{unitId}`, `.../ancestors`, `.../categories` | one unit, its ancestors, its post categories |
| `GET /local/units/{unitId}/members` | its memberships (`org.read` on the unit or above it) |

## Building

```bash
dotnet build
```

```bash
dotnet test
```

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform). Add a migration for every
database provider after a model change:

```powershell
./src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/WebApi.Modules.Organization.Infrastructure -Name <Name> `
    -MigrationsDir Data/Migrations -Namespace soft.square.net.WebApi.Modules.Organization.Infrastructure.Data.Migrations
```

After an endpoint change, export the module's OpenAPI document again (the entry project is `Web`). The next build of
`WebApi.Modules.Organization.Client` regenerates the typed client from it (NSwag); commit both, so client changes show
up in review:

```powershell
./src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/WebApi.Modules.Organization.Web -ModuleId organization `
    -Output <this repo>/src/openapi/organization.json
```

## Releasing

One release is one version for everything: the server manifest, the two client parts and the two packages. It is set
once, in `Directory.Build.props` (`VersionPrefix` and `VersionSuffix`, now `1.0.0` and `preview.1`), and the release tag
is `v` plus that version.

**The bundle.** `scripts/Pack-Bundle.ps1` builds and packs `artifacts/bundle/organization-<version>.zip`, in the layout
of the platform's planned `.modpkg` (its one-step installer is not built yet, so an admin installs the parts in order):

```
module.json                                                      id, name, version, the parts in install order
server/organization-<version>.zip                                upload on /host-modules, activate
client/soft.square.net.WebApi.Modules.Organization.Client.dll    upload on /client-modules, first
client/soft.square.net.Module.Organization.dll                   upload on /client-modules, second
contracts/soft.square.net.Organization.Contracts.<version>.nupkg
contracts/soft.square.net.Organization.Client.<version>.nupkg
```

```powershell
./scripts/Pack-Bundle.ps1                        # the version in Directory.Build.props
```

**The packages.** `.github/workflows/packages.yml` packs two NuGet packages and the bundle on every pull request and
push to `main` (`<VersionPrefix>-ci.<run>`, kept as the workflow's `packages` and `bundle` artifacts), and for a `v*` tag
publishes the packages to the soft-square-net GitHub Packages feed. A tag that does not match the version in
`Directory.Build.props` fails the run before anything is published.

| Package | Project | What |
| --- | --- | --- |
| `soft.square.net.Organization.Contracts` | `src/Organization.Contracts` | DTOs, `org.*` v1 events, `IOrganizationClient`, `IUnitDirectory`, `UnitScopes`, `UnitCategories`, `OrgLiveTopic`; BCL only |
| `soft.square.net.Organization.Client` | `src/WebApi.Modules.Organization.Client` | the typed NSwag client of the API, for callers outside the client module catalog |

**Steps for a release** (the maintainers' decision; nothing in a pull request tags or publishes):

1. Set the version in `Directory.Build.props` and merge it to `main` with green CI.
2. Tag that commit: `git tag v1.0.0-preview.1`, then `git push origin v1.0.0-preview.1`.
3. The Packages run publishes `soft.square.net.Organization.Contracts` and `soft.square.net.Organization.Client`
   `1.0.0-preview.1` and keeps `organization-1.0.0-preview.1.zip` as its `bundle` artifact; attach it to a GitHub
   release if you publish one.
4. Raise the version (for example `preview.2`) for the next changes.

## Installing

The server part is the build output of `WebApi.Modules.Organization.Web` (`bin/<Configuration>/net10.0`: every layer
plus the private Mediator and Ardalis.Result). Zip it and upload it on the client's Host Modules page
(`/host-modules`, as a platform admin), then activate it: in Central mode the central database is migrated on start, and the routes are mapped
under `/api/organization`.

The client parts are two assemblies, uploaded on the client's Client Modules page (`/client-modules`), the API client
first: `soft.square.net.WebApi.Modules.Organization.Client.dll` (hidden; other client modules may depend on it) and
`soft.square.net.Module.Organization.dll` (the Organization pages). The release bundle holds all three (see
"Releasing"), and the playground builds them for you: `playground/out/organization.zip` and `playground/out/client/`.
Then set the mode and the connector on each deployment: [docs/en/setup.md](docs/en/setup.md).

## Developing

`playground/` is an Aspire AppHost with **two deployments** of the platform, both running this module on their core
pool, built from source from a [ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform)
checkout next to this repo:

```
<workspace>/Platform               git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.Organization      this repo
```

(another location: `--property:PlatformRoot=<path>/`).

| Resource | What |
| --- | --- |
| `identity` (5090) | the identity service of both deployments. It registers the connector's service client `organization-connector` (client credentials, scope `api`; the playground uses the service's one configurable service-client slot, `Identity:ElsaClient`), the tenant `newsdesk` and the account `manager@modular.local` in it |
| `central` (5081) | deployment A: Organization in Central mode, `Platform:DeploymentId=central`, its connector pointed at itself; its own PostgreSQL server `central-data` |
| `branch-core` | deployment B: the connector, `Platform:DeploymentId=branch`; its own PostgreSQL server `branch-data` |
| `gateway` (5080) | B's YARP gateway: `/api/organization/local/*` and everything else to B, `/api/organization/*` to A |
| `blzwebclient` (5070) | the Blazor client, on B's gateway |

Both deployments get the connector's settings and its secret as host overrides
(`Modules:Settings:organization:Organization:ClientSecret`; parameter `organization-connector-secret`, a development
value by default), and short intervals (`PollInterval` 5 s, `Tenancy:Seeds:Interval` 15 s). It uses the platform lab's
ports, so stop the lab and any other playground first.

```bash
dotnet run --project playground --launch-profile dev
```

| Profile | What it does |
| --- | --- |
| `dev` (default) | The WebApis load the module straight from `src/WebApi.Modules.Organization.Web/bin/<Configuration>/net10.0` (`Modules:Local`), and the client parts from their build output (`ClientModules:Local`), Development only: installed and active on start. Change code, rebuild, restart `central` and `branch-core` in the dashboard |
| `install` | The platforms start without the module, as in production; upload `playground/out/organization.zip` on each deployment's Host Modules page and activate it, then the two dlls in `playground/out/client/` on the Client Modules page, the API client first |

**The end-to-end demo.** With the playground running:

```powershell
./playground/demo.ps1
```

It signs in as the dev accounts and, on the central service, creates the org `playground-news` with a sector, a
department and a Section with two categories, adds the manager as the Section's `manager`, and creates the seed
`newsdesk` for deployment `branch` rooted at the department, with the manager as its admin. It waits until B reports
`Provisioned`, checks B's replica (the tenant's units, their ancestors, the categories) and the grants (the manager's
position, the seed admin's `unit-admin` and the host's `access.grants.manage`), then renames the Section on the central
service and waits until B's replica has the new name. Every step is idempotent; it exits with 1 when a check fails.

Then sign in on http://localhost:5070 as `admin@modular.local` (tenant `newsdesk`; password in the platform's
`WebApi.Identity.Server/appsettings.Development.json`), open **Organization** > Playground News, and run the script
again: the tree shows the new name within a few seconds, without Refresh. Two playground-only workarounds make this
work, both explained in [Troubleshooting](docs/en/troubleshooting.md): the central deployment has a stub tenant
`newsdesk` (`Playground:CentralKnowsBranchTenants`), and the script grants the admin `org.read` on the org's root unit
in the tenant.

Data stays in the Docker volumes `organization-playground-central` and `organization-playground-branch` and in
`playground/.data`; delete them to start over.
